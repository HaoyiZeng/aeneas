The one thing to keep in mind while reading

Aeneas is written in OCaml and LLBC's semantics lives in Charon, so no Lean theorem can relate wpi to Rust's operational semantics — that link is a trust assumption, and always was. What follows therefore defines the semantics at the ITree level. The ITree is not a compiled artifact; it is the language. This is the same position as the Islaris case study in §7 of Program Logics à la Carte.

So the question this page exists to answer is not "is the compiler correct" but the sharper and more checkable one: does this machine describe the behaviour you intend the generated code to have?

1 · The effect signature

A translated Rust program is an ITree RustEffect α, where

RustEffect = FailE ⊕ₑ ConcE ⊕ₑ StepE ⊕ₑ StateE RustHeap

Four summands, and every observable action of a program is one of them.

Why modify is passed the old heap

The answer type of modify f is RustHeap, and the value handed to the continuation is the heap before the update. This is not a convention that could go either way — it is forced, twice:

  • cas_body reads the pre-state to decide the Bool it returns. Handed the post-state it would always report success.
  • alloc_body returns fresh σ. Handed the post-state it would return a second fresh location, not the one it just allocated.

2 · The heap model is RustBelt's

The heap is not our invention. AccessState is λRust's lock_state, and every operation's enabling condition is one row of λRust's table. This is where the notion of a data race comes from — it is a consequence of the heap model, not an extra definition bolted on.

Why a cell stores a type alongside its value

Val = (T : Type) × T. A heap cell remembers what type it was written at, so an access at a different type is stuck rather than reinterpreting the bytes. Type confusion is therefore an undefined operation, in the same sense as an out-of-bounds access — and both are ruled out by Safe.

One deliberate difference: free

λRust enables free in any lock state and then rules out racing with it by a separate argument. We require reading 0, so freeing a location another thread is reading or writing is simply stuck, and is already excluded by Safe. The same programs are accepted; ours needs no extra argument, at the cost of a free enabled less often.

3 · The heap operations

Each operation is a single modify event, so it is one machine step and therefore atomic. Non-atomic Rust accesses are built from two of them with a yield in between — that is what makes them interruptible, and it is the only reason interference is observable.

The cas rows are worth reading twice. A failed compare-and-swap is only a read, so it is enabled under reading (n+1). A successful one is a write, so under reading (n+1) it is stuck — that is exactly λRust's CasStuckS, and it is a genuine race. A table that lumped all of cas under reading 0 would misdescribe the model.

Because those three rows are the ones most likely to drift from the implementation, they are not left as table entries — each has a theorem:

Non-atomic accesses, and where the interleaving point is

def load_na (l : Loc) : ITree E Val.{u} := do
  let v ← readAcquire l
  let _ ← yield
  let _ ← readRelease l
  return v
def store_na (l : Loc) (v : Val.{u}) : ITree E PUnit.{u+2} := do
  let _ ← writeAcquire l
  let _ ← yield
  writeRelease l v

λRust is a small-step language, so its scheduler may interleave between the two halves of a non-atomic access. We have no scheduler outside the program, so the yield is written into the operation. The effect is the same — the middle of a non-atomic access is exactly where another thread may observe it — but here it is visible in the ITree instead of hidden in a scheduler.

The anti-drift audit

Several of these transformers are written out a second time — in Races.lean, RustBelt.lean and Vacuity.lean — so that theorems can be stated about them directly. A second copy is exactly the hazard λRust's races.v warns about, in a comment it puts above its own duplicated definition:

"This is a crucial definition; if we forget to sync it with head_step, the results proven here are worthless."

A drifted copy does not produce an error. The theorem still compiles and is still true — of a function nothing executes. The defence is that every copy is pinned to the real operation by a rfl lemma, so a divergence becomes a build failure instead of a silently empty theorem. Cooperative scheduling is forced, not chosen

ownE ⊤ — the token that says "all invariants are closed" — is linear. A scheduled thread has spent it; an unscheduled one is an obligation waiting to acquire it. Since it cannot be duplicated, at most one thread can be inside a yield-free region.

Three consequences, none of them stipulated:

  • "Atomic" means "yield-free", not "one step". wpi_open_invariant therefore needs no atomicity side condition.
  • Yielding with an invariant open is unprovable. After inv_acc the thread holds ownD {ι}; yield's first half must produce ownE ⊤ ∋ ι from wsat, whose entry for ι is then in the wrong branch. So the proof cannot be completed — which is what makes the model sound rather than merely convenient.
  • Rust's atomics really are atomic (step; body, no yield), and a non-atomic access is acquire; yield; release.

5 · The machine

A configuration is a thread pool, an index saying which thread holds the big lock, and a heap.

inductive Thread (α : Type) where
  /-- Still running. -/
  | alive (t : Result α)
  /-- Ended by `endthread`. -/
  | dead
structure Config (α : Type) where
  threads : List (Thread α)
  /-- Index into `threads` of the thread that holds the big lock. -/
  current : Nat
  heap : RustHeap.{0}

Step — the whole inductive, as extracted
inductive Step {α : Type} : Config α → Config α → Prop where
  /-- A `step` marker: pure bookkeeping, the heap is untouched. At `.part` this
  is the node whose handler issues the `▷`, i.e. the entry point for Löb. -/
  | tick {c : Config α} {k} :
      c.focus = some (Result.vis stepEv k) →
      Step c (c.setFocus (k PUnit.unit))
  /-- The one state primitive. Note the continuation receives the **old** heap:
  `StateE.O (.modify f) = S`, and `stateH` hands `Ψ s` for the pre-state `s`. -/
  | heap {c : Config α} {f k σ'} :
      c.focus = some (Result.vis (modifyEv f) k) →
      f c.heap = some σ' →
      Step c { c.setFocus (k c.heap) with heap := σ' }
  /-- The only scheduling point. Control may pass to any live thread, including
  the current one. -/
  | yield {c : Config α} {k j} :
      c.focus = some (Result.vis yieldEv k) →
      (c.setFocus (k PUnit.unit)).Alive j →
      Step c { c.setFocus (k PUnit.unit) with current := j }
  /-- Unix-style fork: the *same* continuation is resumed twice, with different
  tags. The child is appended but not scheduled — it becomes eligible at the
  next `yield`, which is what makes `wpi_fork` hand it its obligation under
  `|={⊤,∅}=>`. -/
  | fork {c : Config α} {k} :
      c.focus = some (Result.vis forkEv k) →
      Step c { threads := (c.threads.set c.current (.alive (k ConcE.Tags.cur)))
                            ++ [.alive (k ConcE.Tags.new)],
               current := c.current,
               heap := c.heap }
  /-- End the thread and hand the lock on. -/

      c.focus = some (Result.vis endthreadEv k) →
      c.kill.Alive j →
      Step c { c.kill with current := j }

The rules above are parsed from that inductive, not typed out: premises and conclusion come from splitting each constructor at its top-level arrows, and each rule carries the Lean it came from. Only the notation is a translation table, which is why the source sits beside every rule.

Only the scheduled thread steps, and control moves only at yield and endthread. Since j is existentially quantified in those two rules, quantifying over all reachable configurations quantifies over all schedules. That is why the theorems below need no separate "for every scheduler" clause.

Thread switching, in full

Exactly two of the five rules change current. That is the whole scheduling model, and everything else about interference follows from it.

rulechanges current?to what
ticknothe scheduled thread keeps the lock
heapnolikewise — a heap operation is one uninterruptible step
forkno — current := c.current, explicitlythe child is appended but not scheduled
yieldYESany live j, chosen nondeterministically — including the yielding thread itself
endthreadYESany live j, after the current thread becomes a tombstone

Three consequences worth spelling out, because each is easy to misread:

  • j is existentially quantified, so the machine is nondeterministic. Reaches explores every choice, which is why quantifying over reachable configurations quantifies over all schedules and no theorem here needs a "for every scheduler" clause.
  • yield may choose the current thread itself. It does not force a switch, it permits one. A thread that yields in a loop may run forever without any other thread ever being scheduled — the machine allows that schedule, and it is the reason §7's second gap exists.
  • fork does not switch. The child is appended and is not scheduled; it becomes eligible only at the next yield. This is exactly why wpi_fork hands the child its obligation under |={⊤,∅}=>: the child must acquire the lock before it can run.

There is no preemption rule. Nothing lets the machine take the lock away from a running thread. That is a deliberate choice and it is load-bearing: see §7, where it is both the price paid for a simpler program logic and the source of the one hypothesis pairwiseRaceFree_of_safe cannot discharge.

A schedule, step by step

Vacuity.racer: allocate, fork; the parent yields, the child takes the write lock and yields back, and the parent's own write is then refused. Every line below is one Step in the machine-checked proof race_reachable.

Two things to notice. At step 2 the fork does not hand control to the child — the parent keeps the lock and must reach its yield first. And at step 5 nothing has gone wrong yet: the configuration is faulty because of what the parent is about to do, which is what Config.Faulty says.

The same program with one yield removed

The parent takes the lock and returns. A returned thread takes no step, and yield is the only rule that moves the lock, so the machine stops here — with the child alive and poised on a conflicting write it will never be allowed to attempt.

The two definitions disagree at cStarve, and both halves are proved. λRust calls it a race (two threads poised on conflicting writes); we do not (the scheduled thread's operation succeeds, so nothing is refused). See gap_witness in PairwiseRaces.lean — it is not an argument, it is a theorem.

What can go wrong

def Panics {α : Type} (t : Result α) : Prop :=
  ∃ (e : Error) (k : RustEffect.O (Aeneas.Std.RustEffect.fail e) → Result α),
    t = Result.vis (Aeneas.Std.RustEffect.fail e) k
def StuckOn {α : Type} (σ : RustHeap.{0}) (t : Result α) : Prop :=
  ∃ (f : RustHeap.{0} → Option RustHeap.{0}) (k : RustEffect.O (modifyEv f) → Result α),
    t = Result.vis (modifyEv f) k ∧ f σ = none
def Config.Faulty {α : Type} (c : Config α) : Prop :=
  ∃ t, c.focus = some t ∧ (Panics t ∨ StuckOn c.heap t)

StuckOn is one condition covering four failures: out-of-bounds (the location is absent), use-after-free (likewise, after free), type confusion (Val's type tag disagrees) and a data race (the access state forbids it). They are distinguished in §7.

7 · Data races

Everything so far has been the model. This is the definition that uses it.

def SameContents (σ σ' : RustHeap.{0}) : Prop :=
  ∀ l : Loc, (get? σ l).map Prod.snd = (get? σ' l).map Prod.snd
def RacesOn (σ : RustHeap.{0}) (f : RustHeap.{0} → Option RustHeap.{0}) : Prop :=
  f σ = none ∧ ∃ σ', SameContents σ σ' ∧ (f σ').isSome

Read RacesOn as: the operation is undefined here, and the only thing that would have to change to make it succeed is an access state. The witness heap has the same domain (an Option shape mismatch is already a difference) and the same values. So the failure cannot be out-of-bounds and cannot be type confusion. The access-state discipline is the only thing left to blame — and that discipline is λRust's.

def Config.Racing {α : Type} (c : Config α) : Prop :=
  ∃ (f : RustHeap.{0} → Option RustHeap.{0}) (k : RustEffect.O (modifyEv f) → Result α),
    c.focus = some (Result.vis (modifyEv f) k) ∧ RacesOn c.heap f
def DataRaceFree {α : Type} (t : Result α) : Prop :=
  ∀ c, Reaches (init t) c → ¬ c.Racing

How this differs from λRust's definition — and it does differ

λRust defines a race pairwise over the thread pool:

(* lambda-rust/theories/lang/races.v *)
Definition nonracing_accesses (a1 a2 : access_kind * order) : Prop :=
  match a1, a2 with
  | (_, ScOrd), (_, ScOrd) => True
  | (ReadAcc, _), (ReadAcc, _) => True
  | _, _ => False
  end.

Definition nonracing_threadpool (el : list expr) (σ : state) : Prop :=
  ∀ l a1 a2, next_accesses_threadpool el σ a1 a2 l → nonracing_accesses a1 a2.

Two threads, each about to touch the same location, with an incompatible pair of access kinds. Ours instead looks at the scheduled thread and asks whether it is stuck for an access-state reason. The two are not the same statement, and the honest comparison is:

λRusthere

On programs built from this API the two usually coincide, and the reason is the yield inside every non-atomic access: if two threads are about to perform incompatible accesses, then scheduling one, letting it acquire, and yielding to the other reaches a configuration where the second is stuck. Since DataRaceFree quantifies over all reachable configurations and yield may hand control to any live thread, that schedule is among the reachable ones.

Two places where the difference is real — stated precisely, because the informal version of this claim is too strong.

  1. At a single configuration. λRust flags "both threads about to write, neither stuck yet"; we do not. We flag it one step later, once one of them has acquired. A configuration-local statement is not what DataRaceFree says and would have to be proved separately.
  2. When the racing threads are never scheduled. The argument above needs the currently scheduled thread to reach a yield. If it instead diverges, or returns — which freezes the machine, see §9 — then two parked threads with incompatible pending accesses are never scheduled, no configuration is ever Racing, and DataRaceFree holds while λRust's nonracing_threadpool fails. Ours is a property of executions; λRust's is a property of configurations, and a latent race is invisible to the first.

This is a genuine weakening, not a presentational one. It is stated here rather than left for a reader to find.

The same program, seen by both definitions

Two threads, each performing *x = 1 — a non-atomic write — with x initially reading 0. Non-atomic means writeAcquire; yield; writeRelease.

What makes ours workable at all is the mandatory yield in the middle of every non-atomic access: a real conflict must eventually manifest as stuckness on some schedule, and DataRaceFree quantifies over all reachable configurations while yield may pass control to any live thread.

What each definition buys, and what it costs

Neither is simply better. The trade is worth stating, because it is easy to read the previous paragraphs as "ours happens to be equivalent" — it is not.

The cost line is the one worth dwelling on. λRust's next_access_head is a second description of what the operational semantics already says, and nothing in Coq forces the two to agree — hence the comment above its definition, quoted in §3. RacesOn needs no second description: it is phrased in terms of the transformer f that the machine actually runs, so there is nothing that can drift. That is not cleverness on our part; it falls out of having the state transformer be a first-class value rather than a syntactic form.

The pairwise notion, brought over

Semantics/PairwiseRaces.lean carries λRust's definition across — and in one respect improves on it. λRust needs a second description of its own semantics (next_access_head, classifying redexes into access kinds) which nothing forces to agree with head_step. The version here needs no such thing:

def Conflict (σ : RustHeap.{0}) (f g : RustHeap.{0} → Option RustHeap.{0}) : Prop :=
  (∃ σ', f σ = some σ' ∧ g σ' = none) ∨ (∃ σ', g σ = some σ' ∧ f σ' = none)

Two pending operations conflict when performing one disables the other — stated about the transformers the machine actually runs. No second description, so nothing to keep in sync, and λRust's compatibility table becomes a set of theorems rather than a definition:

The pairwise statement itself is then exactly λRust's:

def Config.RacingPair {α : Type} (c : Config α) : Prop :=
  ∃ i j f g, i ≠ j ∧ PendingOp c i f ∧ PendingOp c j g ∧ Conflict c.heap f g

…and the one hypothesis that cannot be discharged here

Safe constrains the scheduled thread. Turning "threads i and j are poised on conflicting operations" into a contradiction means running i and then scheduling j — and control moves only at yield. So the implication holds, but only under a premise this machine cannot supply, and that premise is given a name rather than hidden:

def SchedulableAfter {α : Type} (t : Result α) (c : Config α) (i j : Nat) : Prop :=
  ∀ f g σ', PendingOp c i f → PendingOp c j g → f c.heap = some σ' →
    ∃ c', Reaches (init t) c' ∧ c'.heap = σ' ∧
      ∃ k, c'.focus = some (Result.vis (modifyEv g) k)
theorem pairwiseRaceFree_of_safe {α : Type} {t : Result α} (hS : Safe t)
    (hsched : ∀ c, Reaches (init t) c → ∀ i j, i ≠ j → SchedulableAfter t c i j) :
    PairwiseRaceFree t := by
  rintro c hc ⟨i, j, f, g, hij, hf, hg, hconf⟩
  rcases hconf with h | h
  · exact not_conflict_left_of_schedulable hS hf hg (hsched c hc i j hij) h
  · exact not_conflict_left_of_schedulable hS hg hf (hsched c hc j i (Ne.symm hij)) h

Both routes to discharging it fail, for the same reason. Operationally, reaching a configuration where j is scheduled needs a Step.yield, hence the current lock holder sitting on a yield — which it need not ever do. In Iris, one might read the premise off SysInv, but a non-scheduled thread's obligation is readyObl = |={⊤,∅}=> runObl and using it spends ownE ⊤, which the scheduled thread has already spent. ownE is not duplicable, so at most one thread's obligation can be opened — the big lock doing its job.

A preemptive machine discharges SchedulableAfter for free. Adding preemption here would break the big lock: preempting mid-computation means parking a thread at mask ⊤, which requires it to hand back ownE ⊤ from inside a yield-free region. The cooperative machine and the atomicity-free wpi_open_invariant are the same decision seen from two sides (§4), and this hypothesis is its price.

A third gap, and the one most likely to bite

RacesOn can only see a race between operations that respect the access-state protocol. Heap.act' takes an arbitrary transformer f : RustHeap → Option RustHeap. A hand-written model that writes fun σ => some (insert σ l (reading 0, v)) — updating a cell without ever consulting or setting its access state — never gets stuck, so RacesOn never fires, so two such threads race in complete silence while DataRaceFree holds.

λRust has no such hole: Read and Write are syntactic forms and are the only way to touch the heap. Here the raw transformer is the escape hatch, and it is not hypothetical — it is exactly what FunsExternal.lean is for.

The practical consequence, stated plainly: race freedom is a claim about code that goes through HeapAPI (which is all Aeneas-generated code), and it is only as good as the hand-written models that sit beside it. A model that bypasses acquire/release does not make the theorem false — it makes it not apply. Reviewing new FunsExternal entries for protocol compliance is therefore part of the trust boundary, not an optional tidiness check.

Then why does λRust not use the weaker, stuck-based definition?

It is the obvious question, and the answer is not "they did not think of it". Compare the two proofs of the same-shaped theorem:

-- here: Safe → DataRaceFree
theorem dataRaceFree_of_safe (h : Safe t) : DataRaceFree t :=
  fun c hr hrace => h c hr hrace.faulty

-- λRust: safety → nonracing_threadpool
Theorem safe_nonracing el σ : ... (* the better part of a hundred lines *)

One line against ninety. That asymmetry is the whole answer: the content is in the definition, not in the proof. Because Racing is a refinement of stuckness, and Safe already says "never stuck", the implication is almost a tautology — it reads "if you never get stuck, you never get stuck in this particular way". λRust's nonracing_threadpool never mentions stuckness, so the gap between it and safety is real and has to be bridged by an argument.

Four consequences, in increasing order of depth.

  1. Their statement is recognisable without reading their semantics. "No two threads are concurrently poised on conflicting accesses, at least one a write, at least one non-atomic" is, near enough, the definition of a data race in the C11 memory model and in the Rust book. Proving that connects the type system to a notion the reader already accepts. "No thread ever gets stuck for an access-state reason" is a statement about the model, and a sceptical reader has to be convinced the model is right first.
  2. Ours leans on a coding convention. Every non-atomic access here is acquire; yield; release, and that yield is what makes a real conflict eventually manifest as stuckness. An ITree that does writeAcquire without the yield, or that calls raw modify, can race in ways RacesOn never observes. λRust assumes nothing about how programs are written.
  3. Race freedom is wanted as a per-configuration fact. A data race is undefined behaviour at the moment the two accesses are concurrent, not at the moment one of them is refused. λRust's statement has that shape; a stuck-based one cannot, because it needs the access to be attempted before it can say anything.
  4. And the deepest one: their machine can schedule any thread at any time; ours cannot. "Thread j is poised to race" is immediately actionable in a small-step language with an external scheduler — j can step next. Here only the lock holder steps, and control moves only at yield, so j may be poised over a conflicting access and unable to move for arbitrarily long, or forever. That is not an oversight: it is the same cooperative discipline that lets wpi_open_invariant dispense with an atomicity side condition (§4). The simpler program logic and the weaker race statement are the same design decision seen from two sides.

So the honest summary is that λRust buys a stronger, standard-facing statement at the price of a second definition that must be kept in sync by hand, and we buy a definition that cannot drift at the price of a weaker statement that leans on how the API is written. Which is the better trade depends on what the statement is for — and if this development ever needs the standard-facing version, adding it is a real piece of work, not a rephrasing.

  ∃ c, Reaches (init t) c ∧ c.current = 0 ∧ c.focus = some (Result.ok v)
def SN {α : Type} (c : Config α) : Prop :=
  Acc (fun c₂ c₁ => Step c₁ c₂) c
def Terminates {α : Type} (t : Result α) : Prop :=
  ∀ c, Reaches (init t) c → SN c ∧ ¬ c.Diverging
'adequacy_part'  depends on axioms: [propext, Classical.choice, Quot.sound]
'adequacy_total' depends on axioms: [propext, Classical.choice, Quot.sound]

Non-vacuity

Every theorem here has the form "nothing bad happens", and such a statement is worth exactly as much as the badness it excludes. If Config.Faulty were unsatisfiable, Safe would hold of every program and adequacy_part would be a tautology — and no amount of worked examples would reveal it, because examples only ever prove the good side.

Semantics/Vacuity.lean proves the other side: panicProg_unsafe and loadProg_unsafe inhabit Panics and StuckOn separately, and racer is a two-thread program with an explicit five-step trace to a racing configuration. The strongest of them is

racer_unprovable : ∀ φ, ¬ ProvableSpecOf .part racer φ

— for a racing program, no wpi triple exists, whatever the postcondition. Race freedom is enforced by the logic, not a coincidence of the examples.

9 · What to check, and what is known wrong

The questions worth asking of this model, and the honest answers.

Known weaknesses

A non-main thread sitting on ret freezes the machine. A returned thread takes no step, and yield is the only rule that changes current. So if the scheduler hands the lock to a thread that then returns, no rule applies and the configuration is final — with other threads still alive and holding pending work. Config.Halted classifies this as a legitimate halt. Rust does the opposite: a spawned thread that returns ends only itself. The fix is a Step rule retiring a non-main returning thread, exactly as endthread does; provable programs are unaffected either way, because the logic already forces a forked child's postcondition to be False.

Nothing is concluded about the final heap. ProvableSpec fixes a pure postcondition, which is forced: fupd_plain_mask needs Plain, and that instance exists only at HasLC.hasNoLC. A consequence is that clients may not use later credits, and there is no wp_invariance analogue here.

Return types are restricted to Type 0. A Rust function returning a Type 1 value is outside these statements. Nothing in the proofs depends on the restriction.

Questions this page is meant to let you answer

  • Is the enabling condition of each heap operation the one you intend? (§2, §3 — each is an ↔, so both directions are checkable.)
  • Is yield in the right place inside load_na / store_na? Everything about interference follows from that placement.
  • Are the five machine rules the ones you want, and is yield's choice of j as unconstrained as you expect? (§5)
  • Is RacesOn the notion of race you want, given that it is manifested rather than potential? (§7)
  • Does every hand-written model in FunsExternal.lean go through acquire/release, or at least never touch a cell whose access state it ignores? A raw transformer bypasses race detection entirely — see the third gap in §7. This is the one caveat that applies to code someone may add tomorrow.
  • Is the ret-freezes-the-machine behaviour acceptable, or should the rule be added? (above)
